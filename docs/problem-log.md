# 问题志（Problem Log）

维护者文档。记录这套编排 skill 在真实需求上踩到的问题、**真实根因**、以及由此落地的规则。

**What this is.** Every rule in `SKILL.md` traces back to a concrete failure recorded here. Read the matching entry **before** changing or removing a rule — several entries record that an obvious-looking alternative was analysed and rejected, and reverting to it would re-introduce a known bug.

**怎么用：**

- 想改 `SKILL.md` 任何一条 → 先在本文件搜该规则对应的编号，看完"真实根因"和"已排除的解释"再动手。
- 要撤销一条规则 → 必须在本文件对应条目**追加**一行"撤销理由 + 日期"，不许静默删除。删了规则又留下条目，下一个人就知道自己面对的是什么。
- 提新建议前先看"已否决"一节，避免重复提已被否掉的方案。

**证据来源：** 条目来自作者一个真实的多里程碑技术需求（约 8 个里程碑，横切多个业务域、含前端改动）在 2026-10 中旬的真实运行，宿主是 **JetBrains IDE 的 Qoder 插件**，不是 Claude Code。具体项目与产物不公开，因此下面只描述机制与可复现的结构，不引用项目内文件名；引用的行号格式（如 `state.md:13`）指该项目里的过程产物，仅作"这条结论有实测支撑"的凭据，不必按图索骥。

> **本文件不要写进任何项目专有信息**：仓库地址、业务域名、类名方法名、上线日期、内部表字段都不行。这份文档是公开的，读者是未来改这套 skill 的人和 agent。

## 一条总的取舍

作者只在**业务复杂**时才走完整对抗评审，也就是说：**这类需求他要的是准确率，不是省 token**。任何"砍评审规模／少生成文件来省成本"的方向对他都是错的。他的原话：

> 我不是觉得新增文件不对……我想要的是前面犯的错能正确继承给后续流程，别重复犯，还要我去纠正。

新增文件本身不构成阻力（前提它承载纠错或环境事实）。判断这套 skill 值不值，用下面 P-07 的体积归因，不要凭感觉。

## P-01 换会话后只做了第一个里程碑，下一个要作者开口才做（2.5.0 / A）

- **现象**：按续接文案开的新会话只规划并执行了当前里程碑，做完就停；作者得自己说"开始下一个"。
- **真实根因**：**不是 bug**。`SKILL.md` 的 just-in-time 原则（"一次只写当前里程碑"）本来就要求单里程碑，交接文案里也写明了范围。缺的是**没人向用户宣告这个边界**——范围只写在文件里，用户只能靠猜。
- **已排除的解释**：agent 不听话／上下文丢了。都不是。
- **落地规则**：断点一节新增「宣告边界」（本会话覆盖哪个里程碑、还剩几个、结束后用户要做什么）；Phase 5 收尾改成**主代理主动产出下一里程碑的续接文案**，不等用户索要。
- **撤销代价**：删掉后用户会以为一个会话该跑完全部里程碑，于是每次都要手动催，体感变成"这流程要人盯着"。

## P-02 里程碑内部不并行，执行慢（未改，C 已否决；D 已加）

- **现象**：单个里程碑里十几个 Task 一条条串行做，太慢。
- **真实根因**（三层，都不是"agent 笨"）：
  1. Phase 3 已把并行决定锁死：上游 `state.md` 里写着"单一 AI 执行流串行拓扑序，无并行泳道、无工期含义"。
  2. 该需求的 DAG 实际是**纯链**，且第一个里程碑是唯一的数据契约节点，后续都依赖它——里程碑级并行无从谈起。
  3. `subagent-driven-development` 在该宿主未安装 → 执行方式退化成 Native（`executing-plans`），而 Native 按定义就是串行。`SKILL.md` 的退路条件写的是"计划薄、任务小时可退到 Native"，而那个计划有 60 多 KB／十几个 Task，**根本不符合"薄"**——退路条件判错了维度。
- **落地规则**：只加了 D（DAG 锁定前把拓扑形状说给用户，纯链时明确"只能串行、总耗时约等于各里程碑之和"并给一次改拆机会）。
- **已否决**：C（计划标注可并行分组 + 执行期按宿主能力并行派发）。作者判断收益不足以抵复杂度。
- **撤销代价**：删 D 之后，用户会在第 3、4 个里程碑才发现"原来这套拆法注定要串行跑 8 轮"。

## P-03 改了已经废弃的逻辑（**未解决**，E/F 仍开放）

- **现象**：作者给了消费方仓库（前端）的地址并说明服务都已启动，agent 仍改了不再使用的分支。
- **真实根因**：
  1. `SKILL.md` 通篇假设**单一代码库**，从未把多仓库／前后端分离当场景；而该里程碑范围里"展示层归属"这类产物的结论**必须**由消费方仓库推出。
  2. 范围用**检索式**定义（按几种调用写法去 grep）——静态检索到的是"有这个调用形状"，不是"有人在用"，死分支和活分支在 grep 结果里长得一样。
  3. 计划头部的 `Code Facts` 只要求"含文件路径"，路径不等于可达性。
- **未落地**：E（Step 0／Phase 1 记全部代码库路径 + 运行时状态作为探索输入）、F（检索式范围强制可达性三态：活跃／仅历史兼容／废弃不改，废弃默认排除并附清单）。E 的路径与运行时状态部分已被 P-06 的环境文档吸收。
- **撤销代价**：无（尚未实现）。**这是当前最大的已知缺口**，下次碰消费方仓库相关的里程碑仍会复发。

## P-04 测试数据要作者手工造（未改，G 已否决）

- **现象**：验收命令要求可跑，但没人准备数据，缺口落在用户身上。
- **真实根因**：Phase 4 的委派输入与产出契约里**没有"数据前提"这一项**；隔离规则文档不等于数据构造。执行端若用便宜模型，更不会自己想到造数据。
- **已否决**：G（计划加 Test Data 段：来源、seed 脚本、隔离清理，缺数据算 `blocked`）。作者认为这本质是"agent 不知道该怎么做测试"，要从别的 skill 找解法，不归本层。
- **撤销代价**：无。

## P-05 已经拍板"不改"的决策，两个里程碑后又被问一遍（2.5.0 / J + L）

- **现象**：作者在 grilling 阶段明确说过某处不改，做到后面又被要求确认。
- **完整链路**（结构上可复现，与具体项目无关）：澄清阶段用户拍板"豁免、不改" → 对抗评审的一个批评者以"无判据、无出口＝无限延期"攻击这条豁免 → 修订记录写成"采纳，经细化"，**把"不改"改写成了"执行期按频度分档再定"** → 这条分档进了里程碑判据 → 执行期实测下来落在低频档，而低频档的处置本来就写着"保留豁免" → **结论与用户最初的答案一字不差**。净信息增益为零，消耗了用户两次确认。
- **真实根因**：① 已定决策没有不可重开的状态位——当时只有评审期间新产生的那批决策被标成"不得重开的根决策"，Phase 1 的早期决策一个都没有；② 分档判据没有默认分支，低频档的处置其实早就定死了；③ 提问前没人查台账（那条决策的结论散在多个过程文件里都能检索到）。
- **落地规则**：J（决策状态位 `locked` / `deferred-with-criteria`，**评审不得把 `locked` 改写成执行期再确认**，只能列 Blocking 交用户改口径）+ L（提问前先按决策编号／文件名／代码路径检索台账，命中即引用原结论）。
- **已否决**：K（`deferred-with-criteria` 必须自带默认分支）。J 生效后这类根本不会被创建成分档，K 的边际收益下降。
- **撤销代价**：删 J 是最坏的一种回退——用户会在执行期被问自己早就答过的问题，这是这套流程**最消耗信任**的失败模式。

## P-06 前置环境条件没往后传播（2.5.0 / H + N）

- **现象**：明明 agent 自己能干的事（读路径、探测端口、连库），换个会话就变成来问用户。
- **真实根因**：环境事实**有被记录**（后续里程碑的计划里有一节"环境/构建（沿用前一里程碑实测）"，含构建工具绝对路径、开发库地址、CLI 正确调用姿势、shell 剥离内联引号的怪癖），但：① `SKILL.md` 规定的计划头部自足三段里**没有 Environment**，那节是计划作者自发加的，于是必然不一致、必然缺项（消费方仓库路径和服务运行状态两处都没有）；② 靠"沿用上一份"**手抄**，每个里程碑重抄一遍就会漂；③ 交接清单每次由 agent 现编，漏什么都不固定。
- **落地规则**：H（单开环境文档，Phase 3 评审收口时建立、只增量更新、各会话只读、计划只引用路径）。这是**作者自己提的方案**，优于我原本"往计划头部加第四段"的做法——后者治不了手抄漂移。
- **落地规则 N**：凭据按来源三分（配置文件有的记路径+键名；用户口头给的账户与口令**原样记进环境文档**；无来源的记成显式缺口）。环境文档因此**永不进提交清单**，头部标"含凭据的过程产物，勿提交"。
- **已否决**：I（外部依赖登记项"先探测后降级"）。作者判断 H 补齐后自然没这问题；若复发再议。注意环境文档里"文档已记的事实不得转成用户问题"一句已沾到 I 的边缘。
- **撤销代价**：删 H 会让每个新里程碑重新问一遍工具路径／库地址／服务状态。

## P-07 "文件这么多，这 skill 真有用吗"（用数据回答）

- **实测**：那次需求的产物全树 60 个 md / 772 KB。按生产者归因：`milestone-planning` 471 KB／26 个（critiques 258 + 骨架草稿 85 + resolution-log 66 + problem-brief 22 + 里程碑定义 34 + state 6）、`writing-plans` 158 KB／7 个、需求本身要求的交付物（契约表／审计清单／runbook／断言）118 KB／25 个、`clarification` 的 Context Brief 14 KB。**编排层净新增：环境文档 + 发现台账 2 类。**
- **结论**：把这套 skill 全卸掉、直接手动跑上游那几个，**这些文件一个都不会少**——它们是上游各自的产物加需求要求的交付物。编排层带来的只有 Phase 2 一次问答、断点续接、Brief 复用为 `Spec:`，以及"完整执行 milestone-planning 不裁剪"这一条。
- **最大的单项成本是 Phase 3 的十几份 critique 逐字稿（258 KB）**，它烧的是**生成**那一次（`SKILL.md` 已规定不回主会话、只回 10 行摘要），不是反复读入。
- **已否决**：轻量评审档（减少镜头数／轮次来省 token）。理由见"一条总的取舍"——复杂路径他要的是准确率。
- **给后来者的方法**：这类"值不值"的质疑，用按生产者拆体积的方式回答，别空口辩护，也别顺手砍评审。

## P-08 相邻两个里程碑各写了一条只差一个参数的查询（2.5.0 / P）

- **现象**：作者怀疑是拆里程碑导致的重复。
- **真实根因**：**不是拆 M 的错**。第一个里程碑冻结的数据契约里**早就预定义**了那条查询（完整谓词 + 统一排序键），但标注"由第 5 个里程碑实现、第 5/6 个消费"；实际执行到第 4 个里程碑就需要它了，复用它等于要提前实现第 5 个里程碑的东西，于是另写了一条——**与契约那条仅差一个可选参数**。而且第 4 个里程碑的计划其实引用过第 2 个里程碑建的同类方法，说明**"看见"不等于"复用"**，缺的是复用判据。
- **落地规则**：P（新建查询／方法／常量前按"表名+谓词族"检索同族实现，命中就复用／加可选参数／在 `Key Decisions` 写明为何必须另开；主代理 Phase 4→5 核对项含此条）+ **契约条目的实现时点不是范围锁**（当前里程碑需要就可提前实现并回写落点，越界只指新增契约之外的字段或口径）。
- **撤销代价**：删掉"实现时点不是范围锁"，同族查重就白写——查到重复也不敢复用。这两条必须同进退。

## P-09 一个窗口跑完全部里程碑，做到后面明显变笨（2.5.0 / R）

- **现象**：很多要点不知道，作者得在它做到一半时喊停纠正。
- **量化**：6 份里程碑计划合计 150 KB，体积单调递减（67.8／28.5／20.9／14.1／9.2／9.9 KB），全树过程产物 772 KB。
- **真实根因**：① 一个会话跑 6 个里程碑本身就绕开了 `SKILL.md` 的断点设计；② 宿主自动压缩会**有损**，被压掉的往往正是最久远的冻结契约与根决策——要点没丢在文件里，丢在历史里；③ **计划越到后面越薄**，书面锚点递减，与记忆失真反向叠加。
- **落地规则**：R（原地继续时每个里程碑仍要**重读而非回忆** Resume／里程碑文件／冻结契约／环境文档／发现台账，冲突以文件为准；开工前 ≤10 行**声明**适用的 `locked` 决策与契约口径，让用户事前纠偏；重新核对未提交改动范围）。
- **注意**：`SKILL.md` 原来只有一句"除非用户明确原地继续"就放行了，对原地继续**没有任何补偿**——这才是缺口。

## P-10 前面犯的错没继承给后面（2.5.0 / T）

- **现象**：执行期纠正过的问题，下一个里程碑又犯，作者只能再纠正一遍。
- **硬证据**：第一个里程碑的收尾文档里记着一条典型执行期发现——验证脚本 `Get-Content $files | Select-String` 误把路径当内容，导致恒 0 匹配 = **假通过**，改成 `Select-String -Path $files` 才对。这条对后续每个验证脚本都成立。但 Phase 4 的委派输入清单里**既没有上一里程碑的 close-out，也没有任何执行期发现汇总**，所以后面只能重新踩或重新想。
- **真实根因**：知识只活在对话里。同窗口时活在历史里 → 被压缩掉（见 P-09）；换窗口时连历史都没了 → 直接丢。**两个失败同源**，所以选哪种窗口策略都不解决，得给执行期发现一个低门槛落点。
- **落地规则**：T（发现台账只追加，一行一条 `日期｜里程碑｜发现或纠正｜类型｜影响哪些后续里程碑｜是否已提升`；用户纠正或实测证伪时**当场**写，Token 纪律的"批量落盘"对它开例外；Phase 4 输入含它，每里程碑必读"本里程碑相关 + 全部标坑的"；能归类的提升进环境文档／契约／词汇表并保留原行；**收尾硬门：用户纠正过的点还只活在对话里 = 里程碑不算关闭**）。
- **已吸收**：S（补充知识当场归位）的判断部分并入 T，不再单独成规。

## P-11 想自动整理 IDE 的变更分组（未做，M 已否决）

- **现象**：作者每做完一个里程碑，手工把改动从 IDE 的活动变更区移出并命名成一个分组。
- **技术结论**：命名 changelist 存在 `.idea/workspace.xml` 的 `ChangeListManager` 里，IDEA 运行时把它攥在内存并回写，agent 从外部改会被覆盖；`.idea` 通常已 gitignore，属纯本机状态。**不可靠自动化，别承诺。**
- **已否决**：我提出的替代方案（收尾产出"改动文件清单 + 建议提交信息 + 可选 `git add` 暂存"）。作者回"不改了"。
- **撤销代价**：无。但**别再次提议**——他要的是知识继承（P-10），不是替他做 IDE 操作。

## 宿主差异备忘

作者日常用 **JetBrains 的 Qoder 插件**，不是 Claude Code。已确认的差异：agent 通常不能主动给用户新建会话（断点全部退化成用户手动）；`subagent-driven-development` 可能未安装，导致执行方式只剩 Native 串行；宿主会自动压缩长会话。**`SKILL.md` 里不要写死宿主工具名**，用"宿主的结构化提问工具""宿主支持并行派发时"这类能力表述。
