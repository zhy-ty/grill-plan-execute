# Grill, Plan, Execute

## Overview

只编排外部 skill，定义阶段边界、完成判据与交接契约，不复制上游正文。流程：访谈 → 用户确认复杂度 → 复杂才走里程碑规划与对抗性评审 → 逐里程碑出计划 → 用户选择后移交执行。按检查点恢复规划，不依赖完整访谈历史；环境事实集中在一份环境文档、纠错集中在一份发现台账，各会话只读它们。**执行会话不加载本 skill，所以要求它遵守的义务随计划文档走，不随本文件走。**

安装、依赖明细、扩展指南与兄弟 skill 对照表见 README；本文件只放运行时规则。

## Output language（面向用户的语言）

本文件的中文是写给 agent 的指令，不是给用户看的台词。**所有面向用户的输出——提问、选项标签、阶段报告、缺失依赖的补齐指引——一律跟随用户当前使用的语言**，用户用英文就整句英文，不要中英混排。

下文给出提问原文处都并列 EN / 中文 两版：按用户语言取其中一版发给用户，**不要把另一版一起显示**。

## Token 纪律

- **路径交接，按需读取。** 传任务范围、必要决策和产物路径，不重贴全文或复述依赖规则；不能为了短摘要省略阻塞信息。
- **按主题批量落盘。** 一个主题确认后统一更新术语、决策与假设；转阶段或结束会话前写完，不随每条回答重写文件。环境事实集中在环境文档，计划与简报只引用路径，不逐份复制。发现台账是这条的例外：纠错要当场追加一行，攒着就会丢。
- **隔离重活。** 探索、批评、写计划交给能加载所需 skill 的 subagent，给最小必要上下文，产物落盘、回摘要；不要假设宿主不会继承历史。
- **计划 just-in-time。** 一次只写当前里程碑，后续根据实际代码状态规划。
- **检查点续接。** 按下节切换上下文；写文件本身不会清除历史，subagent 的输入输出同样消耗 token。

## Dependencies

四个必需项，按命名空间引用，本仓库不含这些 skill 的文件：

- `mattpocock-skills:grilling` — 决策树式多轮访谈，产出共识理解
- `mattpocock-skills:domain-modeling` — 实时维护领域词汇与决策记录
- `engineering-discipline:milestone-planning` — 并行探索 → 里程碑 DAG → 对抗性评审（仅复杂路径）
- `superpowers:writing-plans` — 面向零上下文工程师的详细实现计划

另需**格式资源**：`engineering-discipline:clarification` 的 Context Brief 模板与 Complexity Assessment 评分规则。只读取，不运行其访谈；资源缺失会阻塞完整工作流，不能把它当成可选项。

`references/templates/` 下是本仓库**自有产物的版式**（执行契约、规划登记表、过程文件版式），不含任何上游正文，不受零副本约束。

可选项（缺失不阻塞，只告知用户）：

- `mattpocock-skills:grill-with-docs` — 一次调用依次跑上面前两个
- `superpowers:subagent-driven-development`、`superpowers:executing-plans`、`superpowers:finishing-a-development-branch` — Phase 5 移交目标
- `superpowers:verification-before-completion`、`engineering-discipline:review-work` — Phase 5 评审兜底，强烈建议；执行端用便宜模型时实际必配

Plugin 整包安装，CC Switch 需手工安装；命名空间不带插件前缀时使用已注册的裸名。安装与版本见 README。

### Step 0: 自检

从宿主索引确认当前所需 skill 可用，不提前加载后续阶段正文。完整工作流开始访谈前，还要在已安装插件或本地上游目录定位 `clarification`，只读取 Context Brief 模板及评分规则，记录来源路径。缺必需 skill 或资源就停下，按分发方式给补齐指引；**不猜格式、不编分数、不凭记忆模拟**。

可选项缺失不阻塞：`grill-with-docs` 缺失就调 `grilling` + `domain-modeling`；执行类 skill 缺失就交计划给用户自行执行；评审兜底项缺失则告知用户"缺少独立验证，建议人工复核"。

### 宿主能力探测

开始完整工作流时探测下列能力，结果写进 Workflow Resume；环境文档建立后并入环境文档，此后 Resume 只留指针，后续会话不重复探测：

- 能否由 agent 新建会话；是否有结构化提问工具；能否派发 subagent（**不承诺并行**）。
- 执行类 skill（`executing-plans`、`subagent-driven-development`、`finishing-a-development-branch`、两个评审兜底项）哪些实际可用。

任一项为否，就在续接宣告文案或 Phase 5 已有的那次询问里点名该差异与它的代价，由用户决定，不默认降级、不假装宿主具备能力。**"当前里程碑计划能否被单个上下文完整持有"不在这里判**——计划要到 Phase 4 才存在，判它得等计划写完（见 Phase 4）。

### 上游契约锚点

本 skill 的编排契约挂在上游的具体产物上，上游改版会静默失效。Step 0 只读上游 `SKILL.md` 的相关小节（`clarification` 的模板与评分规则沿用上面已规定的资源定位动作，不限定只读文件头部），校验四个锚点并把结果写进 Workflow Resume：

1. 执行方式选项名（是否仍叫 `Subagent-driven` / `Native`）
2. 评审产物路径（critiques 目录与 resolution-log）
3. Context Brief 模板字段（含 `Complexity Assessment` 是否存在）
4. 评审轮次参数

命中记"已验证版本"；不匹配记"契约差异 + 差异内容"，按上游实际值执行并告知用户，不假装兼容。**四个锚点一个都没读到就停下，不进 Phase 1**——后续完成判据全靠它们定位，凭记忆填等于猜。不做全量比对。自有轮次上限（见 Phase 3）与上游轮次参数分开记：执行按自有上限，上游值只用于报告规模与路径。

### 上下文断点与恢复

在 Context Brief 末尾维护简短的 **Workflow Resume** 续接索引，批量更新，不另建平行进度表：

- 下一阶段、用户确认的复杂度、当前里程碑、DAG 是否已锁定、执行方式是否已选择；未确认项明确标为待定。
- 模板来源、词汇表、决策、环境文档、发现台账、当前草稿／就绪计划及状态、复杂路径 `state.md` 等必要路径；里程碑状态以上游 `state.md` 为准，不复制整份 DAG 或评审日志。
- 未决阻塞项、用户接受的非阻塞假设及其复核时点；详情引用原章节。
- 代码事实的版本基线（Git 项目记 HEAD 与未提交改动范围）和当前里程碑的验证结果／证据路径。
- 宿主能力探测结果与上游契约锚点结论（环境文档建立后这两项并入环境文档，Resume 只留指针）；假设登记表与 `locked` 决策索引的路径。

**断点：** Phase 1 共识与 Phase 2 选择完成后、Phase 3 的 DAG 确认锁定后、每个里程碑执行与收尾完成后，更新索引再用新上下文进入下一阶段。宿主不能开新会话时用实际可用的压缩能力；两者都没有就给出续接指令由用户开新会话，除非用户明确原地继续。不要声称写文件已清空历史。

**宣告边界：** 把续接文案交给用户时，同一句话里说清本会话只覆盖哪一个里程碑或哪一个阶段、DAG 里还剩几个未完成、以及会话结束后需要用户做什么（通常是开新会话并粘贴本文案）。范围只写在文件里而不说给用户，等同于没写；用户不该靠猜。

同一份文案还要带上本阶段完成判据的核对结果，3–5 行，**只列用户能验证或能决策的项**：本会话覆盖范围、剩余里程碑数、未决阻塞、执行方式授权状态、尚未落盘的用户纠正点。未满足项点名并说明缺什么；全部满足就写一行"以上判据均已满足"。不向用户输出内部全量核对过程，也不因此多问一次——各 Phase 的完成判据仍是主代理自核，不成交互门。崩溃或中断后的进度以**计划文档里的 Task 勾选状态**为准，由这份文案报出，不另建进度字段。

**原地继续也要以文件为准**：用户明确选择同一会话连做多个里程碑时（宿主压缩会让历史失真，且越到后面越不可靠），每个里程碑开工前仍然**重新读取而非回忆**：Workflow Resume、当前里程碑文件、冻结契约、环境文档、发现台账；与对话历史冲突时一律以文件为准。开工前用 10 行以内声明本里程碑适用的 `locked` 决策与契约口径，给用户一次当场纠偏的机会——纠偏要前置，不要做一半被喊停。同时重新核对未提交改动范围，不沿用上一个里程碑开始时的基线。

**恢复：** 只携带本 skill 的调用入口、Context Brief、环境文档与发现台账路径、下一阶段；读取续接索引及本阶段所需文件，不重读全部访谈或批评记录。核对阶段完成状态、相关代码变更和到期假设；未提交改动也要核对，不能只比较 HEAD。事实失效时只补查受影响范围；决策需变更则请用户重新确认受影响项，不重跑整个访谈或重复询问未变化的复杂度。续接信息不构成开始实现的授权。

### 环境文档

单开一份环境事实文件，供所有规划与执行会话只读，避免逐里程碑手抄漂移：

```
docs/engineering-discipline/context/YYYY-MM-DD-<topic>-environment.md
```

- **内容**：全部代码库清单（含工作区之外的消费方仓库，如前端，一律记绝对路径）；构建与验证命令的绝对路径（JDK、Maven、CLI 可执行文件）；数据库与服务的地址、端口、库名；运行时状态（服务是否已启动、可访问入口、探测命令）；宿主 shell 的已知怪癖与规避写法；宿主能力探测结果与上游契约锚点结论。版式见 `references/templates/process-artifact-layouts.md`。
- **显式缺口**：查不到又拿不到的事实不许留空、不许靠默认答案绕过，写成条目并带三个字段：`最迟复核时点｜影响哪些里程碑｜是否阻塞当前里程碑`。阻塞项必须在当前里程碑委派前解决或转成用户问题；不阻塞项可以带缺口继续，但到复核时点必须核一次，到期未回填就记进发现台账，不许静默放过。
- **凭据按来源记录**：配置文件里已有的，记文件路径与键名，不抄值；用户在对话中口头给出的账户与口令，**原样记进本文件**并写明用途（如"xx 账户可用于测试环境 HIS 推送"）；既无来源也拿不到的，记成显式缺口，不许靠默认答案绕过。
- **定位**：本文件可能含凭据，因此**不进提交清单**，头部固定写一行"含凭据的过程产物，勿提交"。它与 Context Brief、计划、评审产物同属过程产物——要不要入库由用户定，但跨需求留存的结论与理由必须落在 ADR 与词汇表里（见 Phase 5 收尾），不能只活在过程文档里。
- **建立时点**：复杂路径在 Phase 3 评审收口、DAG 锁定前建立，内容取自 Context Brief 的 `Technical Context` 与探索、批评期间实测到的事实；**不复杂路径由主代理在 Phase 4 首次委派之前建立**——Phase 4 的委派输入含本文件，等写计划的子代理去建它就成了"输入含它、它还不存在"的死锁。这一步只要求**文件建出来**，内容允许带显式缺口；连文件都建不出来（目录不可写、路径没定）才算缺依赖，报 `blocked` 不委派。建立的同时把 Context Brief 里那份代码库清单换成本文件的指针，不两处维护。
- **更新方式**：仅在事实变化或被实测证伪时**增量改对应条目**，不整体重写，也不随每条访谈回答改动。
- **交接**：路径写进 Workflow Resume；Phase 4 的委派输入和每个执行会话的必带清单都含它。计划文档不复制这节内容，只引用路径。
- **不得转成用户问题**：文档里已有的事实（路径、地址、服务状态）由会话自己读取或按记录的探测命令实测，不再向用户复述询问。

### 发现台账（discoveries）

一份追加式清单，专门承载**前面犯的错和前面被纠正的点**，让它们继承给后续流程：

```
docs/engineering-discipline/context/YYYY-MM-DD-<topic>-discoveries.md
```

条目六字段顺序固定：`日期｜产生里程碑｜一句话发现或纠正｜类型（环境事实／契约口径／术语／决策／坑）｜影响哪些后续里程碑｜状态`。状态取四值之一：`生效`、`promoted→目标文件`、`superseded→新条目`、`stale@日期`——被正式文件吸收记 promoted，被后续条目推翻记 superseded 且两行都留着，存疑但尚未证伪记 `stale@日期`。样例版式见 `references/templates/process-artifact-layouts.md`；字段与状态语义只在本节定义，模板不重复定义。

- **谁写**：任何会话——规划、评审、执行——只要**用户纠正了 agent**，或**实测证伪了既有认知**（含假通过的验证脚本、误判的可达性、契约里过时的表述），当场追加一条。不确定归哪类也先记，别丢在对话里。执行会话是从计划的 `Execution Contract` 收到这条义务的，不靠本文件——它不加载本 skill。
- **谁读**：Phase 4 的委派输入含它；每个里程碑开工前必读**本里程碑相关的条目 + 全部标"坑"的条目**（坑跨里程碑通用，例如"用路径当内容去 grep 会恒 0 匹配"）。
- **提升**：条目能归类时写进正式文件（环境文档／冻结契约／词汇表／ADR），原条目标 `promoted→目标`，不删除，保留可追溯。
- **边界**：Workflow Resume 只记本文件路径，不复制条目；台账不写过程流水账，**也不写里程碑进度**（进度以计划文档的 Task 勾选为准），只写"以后会因此改变做法"的东西。

## Workflow

### Phase 1: 澄清与领域建模

调用 `mattpocock-skills:grilling` 访谈，配合 `mattpocock-skills:domain-modeling` 按主题批量更新术语与决策。可用 `grill-with-docs` 作为入口，宿主拒绝触发时退回两个独立调用。用户明确只要访谈、不写文档时，只需 `grilling`，不检查模板资源，也不继续 Phase 2–5。

把本阶段停止条件作为访谈边界交给 `grilling`：**目标、范围／非目标、约束与验收标准已确认，且没有阻塞当前规划的问题。** 不为穷尽设计树无限追问；能查证的环境事实交给探索，不让用户回答，也不复述探索过程。

非阻塞问题经用户接受后记为显式假设，并注明受影响里程碑或最迟复核时点；规划或执行受影响工作前必须复核。会影响安全、权限、数据一致性、不可逆迁移或使范围／验收无法确定的问题仍是阻塞项，不能靠延期或默认答案放行。

**假设登记表**：这些假设集中成一张表，不散在访谈记录里：`编号｜假设内容｜受影响里程碑｜最迟复核时点｜状态（待复核／已验证／已证伪）`，版式见 `references/templates/planning-registers.md`。复核触发点固定三处——**Phase 3 规划前**（假设会影响里程碑划分时）、**Phase 4 开工前**、**Phase 5 里程碑收尾**，不写"定期复核"，没有时点的纪律等于没有纪律。

**决策状态位**：访谈中每条由用户拍板的决策，落盘时标注 `locked`（结论已定，不得重开）或 `deferred-with-criteria`（用户授权执行期按判据自决）。用户在 grilling 阶段给出的"这里不改／不动"就是 `locked`，不是待验证的假设。Phase 3 的批评与修订**不得把 `locked` 决策改写成执行期再确认**；批评者认为它缺判据、缺出口或有冲突时，只能作为 Blocking 项升级给用户改口径，由用户决定换不换状态。评审能加判据的只有 `deferred-with-criteria`。

**`locked` 决策索引**：把上述两类决策汇成一张索引：`ID｜状态｜一句话结论｜出处｜影响哪些里程碑`，版式同上。它是 Phase 3 批评者的输入之一，也是 Phase 5 提问前的第一个查询点。索引只做查询入口，**结论详情仍以原决策记录为唯一来源**，不在索引里复制论证。

**交付 Context Brief**：按 Step 0 实际读取的上游模板与评分规则写，不额外运行 `clarification` 访谈，也不在本仓库复制模板：

```
docs/engineering-discipline/context/YYYY-MM-DD-<topic>-brief.md
```

`Technical Context` 记录代码事实、文件路径与版本基线，供后续从已知事实起步；`Complexity Assessment` 按上游规则填，作为 Phase 2 推荐依据。**全部代码库清单（含工作区之外的消费方仓库，绝对路径）与运行时状态必须在 Phase 1 就登记进 `Technical Context`**：Phase 3 的并行探索要拿它当输入，而环境文档按规则要到 Phase 3 收口才建立，等不到。环境文档一旦建立，这段就换成指向它的指针，不两处维护；其余工具绝对路径、连接方式这类环境事实从一开始就按「环境文档」一节单独立文件，Brief 只留影响本需求的结论与指向路径。Phase 3 消费本文件，Phase 4 的 `Spec:` 指向它。**不要提前造 `Problem Brief`**，它由 `milestone-planning` 探索后生成。

**完成判据：** 上述停止条件满足，用户确认需求与保留的假设，Context Brief、词汇表和决策记录已写完。随后进行 Phase 2，不在这里重复访谈。

### Phase 2: 复杂度评估

用宿主的结构化提问工具（如 `AskUserQuestion`）以**选项式**问用户，两个选项 `Complex / 复杂` 与 `Not complex / 不复杂`；宿主没有该工具时退化为纯文本 Y/N 提问。提问时把 Context Brief 里 `Complexity Assessment` 的分数与 verdict 一并报给用户作为你的推荐，下面的判断标准只是给用户的解释口径。提问正文按 Output language 一节取用户语言的那一版，原文如下：

> **EN:** "Based on what we've settled so far — is the business logic here complex? Rule of thumb: complex means more than 8 implementation steps, or more than 3 core modules to modify or understand. If it's complex, I'll run a deep code exploration plus adversarial review to catch gaps before splitting milestones; if not, I'll go straight to one implementation plan."
>
> **中文：** "根据当前理解，这个任务的业务逻辑是否复杂？判断标准：预计实现步骤超过 8 个，或需要修改/理解超过 3 个核心模块，就算复杂。复杂的话我会先做深入的代码探索和对抗性评审来查缺补漏，再拆里程碑；不复杂就直接出一份实现计划。"

- 用户选 **Not complex / 不复杂** → 跳到 Phase 4
- 用户选 **Complex / 复杂** → 进入 Phase 3

这个判断权在用户，不要替他决定，也不要因为"看起来简单"就跳过这一步。将用户选择与下一阶段写入 Workflow Resume，按断点规则续接。

### Phase 3: 里程碑规划（仅复杂路径）

调用 `engineering-discipline:milestone-planning`，**完整执行它的流程**，不裁剪：并行探索 → 两副骨架起草 → 独立批评者并行对抗评审 → 修订直到无 Blocking（唯一偏离是下面的轮次上限，它限制循环次数，不取消评审）。这一步不能压缩成"顺手拆几个里程碑"——评审的意义正是让独立批评者基于代码事实攻击这份划分。

把 Phase 1 的 Context Brief、词汇表、决策记录、**`locked` 决策索引与假设登记表**以**文件路径**交给它，不要复述全文。进入规划前先复核一遍影响里程碑划分的假设（三处复核点的第一处）。它自己的 Problem Brief 与 Exploration Digest 由它探索后 compose，不要替它写。评审攻击的是里程碑划分、判据与出口，**不是用户已拍板的 `locked` 决策**（见 Phase 1「决策状态位」）；批评者指出某个 `locked` 结论缺判据或与验收冲突时，只能把它列成 Blocking 交用户裁决，修订方不得自行把它降级成执行期再确认。

**评审产物落盘，只回摘要。** 批评者产物的目录与文件名**取 Step 0 锚点读到的上游路径**（上游当前写法是 `docs/engineering-discipline/harness/<slug>/planning/critiques/round-N-<lens>.md`，逐字记录汇总进同目录 `resolution-log.md`；上游改版就按它实际的来，不照抄记忆）。据此要求每个批评者 subagent：完整 findings 写进自己那个文件，**回主会话的正文压到 10 行以内**（各严重度计数 + 每条 Blocking 一句话 + 文件路径）。resolution log 引用路径，不把全文抄进对话。这不削弱评审——逐字记录一条不少，只是不进主上下文。

**评审轮次上限：** 本工作流**写死最多 2 轮**修订（实践中大多在第二轮前收敛），这一条不随上游版本变化；每轮包含"多个批评者 + 修订 + 再评审"，是整个流程成本最高的一环。批评者数量与上游自己的轮次参数按 Step 0 读到的上游值报告给用户，**不参与本工作流的上限判断**。两轮后仍有 Blocking 就**不要继续自动修订**：把未决分歧整理成清单（批评者论点、作者回应、未解决项，各项指向 critiques 文件路径）交用户人工裁决，拍板后锁定 DAG 进入 Phase 4。收轮次靠把交接信息给足，不靠削弱评审。

**锁定前把拓扑形状说给用户**：DAG 交付确认时报告里程碑之间是否存在可并发的分支。若整张图是一条纯链、没有任何并发分支，明确说明"这个拆法只能串行执行，总耗时约等于各里程碑之和"，并给用户一次改拆的机会（比如合并相邻同域里程碑、或把只依赖前序数据的展示类里程碑并成一批）。不替用户决定要不要并行，也不用"串行更安全"含糊带过。

**完成判据：** 里程碑 DAG 通过评审且用户确认锁定；或到达轮次上限后由用户裁决遗留分歧并经用户确认。产出：`harness/<slug>/` 下 `state.md`、`milestones/M*.md`、`planning/problem-brief.md`、`planning/resolution-log.md` 的路径，以及本阶段收口时建立的**环境文档**路径。环境文档"建立完成"含三个动作：文件写出来、宿主能力与锚点结论并进来、Context Brief 里那份代码库清单换成指针——缺任一项不算建立完成。更新 Workflow Resume，按断点规则进入 Phase 4。

### Phase 4: 生成执行计划——一次只做一个里程碑

按依赖顺序选择一个就绪里程碑；不复杂路径处理整体任务。先核对到期假设、相关代码变化与验收目标，并对准备新建的查询与方法做同族查重（见下），再写计划，不提前写后续里程碑。

**委派契约：** 让能加载 `superpowers:writing-plans` 的 subagent 按上游步骤只写当前范围的计划；给出范围、验收目标及以下路径，不转发访谈历史。不支持此委派时，在新规划上下文由主代理调用该 skill。两者都不得自行实现、合并或替用户选择执行方式。输入文件：

- 当前里程碑的 `milestones/Mk-<name>.md`（不复杂路径没有这一项）
- Phase 1 的 Context Brief —— 填进计划头部的 `Spec:` 字段
- **环境文档**（构建命令、连接方式、消费方仓库路径、运行时状态、显式缺口）—— 计划只引用路径，不复制正文
- **发现台账** —— 本里程碑相关条目 + 全部标"坑"的条目，作为已知前提；计划不得重复犯台账里已记录的错
- **`Execution Contract` 模板正文**（`references/templates/execution-contract.md` 的内容，由主代理读出来直接贴进委派输入）—— 委派子代理能否解析本仓库的相对路径不由我们保证，所以给正文不给路径
- 复杂路径再加 `planning/problem-brief.md`（含 Exploration Digest）与 `planning/resolution-log.md`
- 词汇表、决策记录文件，以及 `locked` 决策索引与假设登记表

**新建前先做同族查重。** 计划里每个准备新建的查询、方法、常量或映射表，先在既有代码与已冻结的契约文档里按"表名 + 谓词族"或"键名 + 语义"检索同族实现。命中就三选一：直接复用、给它加一个可选参数、或在计划的 `Key Decisions` 里写明为什么必须另开一条。不许静默新建近重复——只差一个参数的两条查询会在后续里程碑各自漂移，连契约里统一过的排序键都守不住。

**契约条目的实现时点不是范围锁**：冻结契约里标注"由 Mx 实现、My 消费"的条目，若当前里程碑就需要它，可以在当前里程碑提前实现——条目内容已冻结，只是时点前移，不算越出范围；越界指的是新增契约之外的字段或口径。提前实现后回写该契约，把实现里程碑改成实际那个。

**可达性三态。** 凡靠检索定范围（grep 调用形状、按名字找引用）的结论，必须标三态之一：

- `活跃` —— 有可达的消费方，附证据：消费方仓库里的命中位置，或环境文档记录的运行时可达性
- `仅历史兼容` —— 保留但不改行为
- `废弃不改` —— 默认排除，并在计划里列出排除项与依据

静态检索到"有这个调用形状"不等于"有人在用"，死分支和活分支在 grep 结果里长得一样。判 `活跃` 需要消费方仓库或运行时证据。环境文档里没有这类证据时，先按它记录的路径与探测命令自己取证、去消费方仓库查，并检索 `locked` 决策与台账；**只有取证已试过仍缺、且该缺口阻塞本里程碑范围或验收时**，才按 `needs-input` 交用户，问题里附上已查路径、已执行命令与失败输出。"环境文档没写"本身不是问用户的理由；不阻塞的缺口记成显式假设带复核时点，不打断用户。计划头部的 `Code Facts` 每条都要带"谁在用"。

子代理返回状态，不把计划正文贴回主会话：

- **`needs-input`**：上游需要用户答复时，返回具体问题、必要上下文／选项及已有草稿路径，暂停。主代理转达并记录答案，再从草稿继续，不重新访谈或从头生成。
- **`plan-ready`**：计划路径 + ≤5 行摘要（目标、任务数、验收命令）；上游提供的执行方式选项另附，交 Phase 5 由主代理询问。
- **`blocked`**：缺依赖、输入不可读或契约不兼容时，返回缺项与已有草稿路径，不猜测补齐，也不伪报完成。阻塞信息和用户问题不受摘要行数限制。

任何暂停前，主代理都要将状态、已有草稿路径和待解问题写入 Workflow Resume；解除阻塞或重新委派后从该草稿继续。草稿不能当作就绪计划执行。

主代理核对实际计划的范围、验收条件与交接字段，并确认：每个新建项已按同族查重给出复用结论或 `Key Decisions` 理由；检索式范围已标可达性三态；`Execution Contract` 一节在、四段齐、每个 Task 末尾的义务短句在。三项都核完才进入 Phase 5；收到摘要不等于计划已通过检查。

**计划可持有性在这里判，不在 Step 0 判**：计划写完后，主代理按它的体积与 Task 数判断"能否被单个上下文完整持有"，结论写进 Workflow Resume，供 Phase 5 选执行方式使用。

保存路径由 `writing-plans` 决定（默认 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`）；复杂路径下文件名带里程碑编号，避免覆盖。

计划头部保留四段自足内容，供不带访谈历史的会话接手。**执行会话不加载本 skill，所以凡要求它遵守的规则必须写在这份计划里——只写在 `SKILL.md` 对它等于没写**：

- **Domain Context** — 本里程碑涉及的核心术语
- **Key Decisions** — 已经定下的设计决策，含出处
- **Code Facts** — 探索得到的关键事实，含文件路径**与"谁在用"**
- **Execution Contract** — 按 `references/templates/execution-contract.md` 实例化本里程碑的执行期义务，**正文写进计划**，不只给路径；写计划的子代理同时负责把每个 Task 末尾的义务短句一并写进去

环境类事实不进这四段，计划里只写环境文档与发现台账的路径，由执行会话自己读取；但"必须去读它们"这件事本身是执行义务，因此必须出现在 `Execution Contract` 正文里。每个 Task 末尾再内联 3–5 行**本任务适用的义务短句**：全局义务（纠正当场追加台账、完成 Task 就勾选、无验证证据不许声称完成）每个 Task 都出现；任务特有义务列在该 Task 下。**不许用编号引用计划头部**——任务级上下文未必带着头部，编号会指向它读不到的地方；宁可重复短句，也不留悬空引用。

计划就绪后更新 Workflow Resume 中的计划路径，标明是否仍待执行方式确认。执行默认新会话，只带当前计划、必要引用及用户已确认的执行选择，不带完整规划历史；会话能力不足时按断点规则处理。

### Phase 5: 移交执行

**用户交互由主代理负责。** 依据 `writing-plans` 当前版本的执行选项，用用户语言解释代价并询问；子代理返回的问题由主代理转达，不让它自行跨入执行。选择已经通过主代理确认并记录在当前里程碑的 Workflow Resume 中时，不重复问；未确认则等待，不能自行开始实现。

**提问前先查台账。** 任何准备抛给用户的问题——包括转达子代理问题之前——先查 `locked` 决策索引（它是为这一问准备的入口），再按决策编号、文件名、代码路径检索决策记录与 Workflow Resume。命中已有结论就直接引用该结论继续执行，不重问一遍；只有当新证据与原结论冲突时才升级，并附上冲突证据与出处。用户在 grilling 阶段拍板过的"这里不改"被执行期再次问出口，是这套流程最消耗信任的失败。**执行会话也要遵守这条，靠的是每份计划里的 `Execution Contract`，不是本节。**

保留选项名 `Subagent-driven` / `Native`：分别转交 `superpowers:subagent-driven-development` / `superpowers:executing-plans`；若上游版本不再提供对应选项，先说明契约差异，不假装兼容。两条路做完都进入 `superpowers:finishing-a-development-branch`，由它给 merge / PR / cleanup 选项。

**模型分层（默认建议）：** 强模型规划与评审，便宜模型按计划执行。自足计划降低对访谈历史的依赖，不保证低推理能力模型能正确完成；根据验证与返工情况判断是否需强模型执行。执行端配验证与独立评审：

- `superpowers:verification-before-completion` —— 执行者自证：没有新鲜的验证证据（当场跑测试/构建并读输出）不许声称完成
- `engineering-discipline:review-work` —— 独立他证：只用计划文档 + 代码库判定实现是否符合计划，结论落成文档；由**强模型**跑，天然与"执行开新会话"对齐

这两个 skill 缺失时不阻塞，但要告知用户"缺少独立验证，建议人工复核"。

**搭配默认：** `Subagent-driven` + 便宜模型执行 + 强模型评审——每任务一份新上下文，天然就是模型与上下文的断点。退到 `Native` 的判据是"**本里程碑计划可被单个上下文完整持有，且任务之间无跨任务契约依赖**"（用 Phase 4 记下的可持有性结论，**不是"计划看起来薄"**——实测里按体积观感误判过一次，把十几个 Task、六十多 KB 的计划退成了串行）；不满足就用 `Subagent-driven`，该 skill 在当前宿主不可用时，明确告诉用户缺什么、退化成串行的代价是什么，由用户选，不自动降级。意外决策多、便宜模型覆盖不了时才全程强模型。

本里程碑执行与收尾都走完，核对验证证据并更新上游状态与 Workflow Resume；仍有未完成里程碑就**由主代理主动产出下一里程碑的续接文案并交付用户**，按断点规则回 Phase 4，不等用户开口索要——用户不该负责串起流程的下一环。全部里程碑结束才收尾。下一里程碑的执行选择重新标为待定，不跨里程碑沿用授权，也不在当前里程碑中途串用执行方式。

**close-out 是执行会话的产物。** 本里程碑的收尾报告落在**与当前计划同一目录**，文件名沿用计划名加 `-close-out.md`。它由执行会话产出（义务经计划的 `Execution Contract` 送达——它不加载本 skill），主代理在 Phase 5 读取并核对。必含三行：

- `本里程碑发现：无` 或发现清单（清单里每条都已同步追加进发现台账）
- 验证证据：当场跑过的命令 + 输出摘要 + 证据文件路径
- Task 完成度 x/y（y 取自计划文档）

**"无"、"不确定"、"blocked" 都是合法输出，不许为了好看编内容**：没跑验证就写 blocked 而不是写结论；拿不到 Task 总数就写"不确定"。收尾门**只核「本里程碑发现」这一行在不在，不核台账有没有变长**——干净里程碑就该写"无"，逼着增长只会污染之后每个里程碑都要必读的坑清单。此外核对还有没有只活在对话里的用户纠正点，有就不算收尾完成；能归类的顺手提升进环境文档、冻结契约或词汇表。

**把理由搬出过程文档**：Context Brief、`resolution-log`、critiques、计划、环境文档、发现台账都是过程产物——要不要入库由用户定，但下一个需求不会回头读它们。因此每个里程碑收尾时，凡**只有过程文档承载的决策理由**——尤其是"这块为什么不改""为什么豁免""为什么废弃不处理"这类负向决策——要写进 ADR 或词汇表条目，附出处编号。全部里程碑结束时复核一遍：过程文档里没有本该进 ADR 却未落的理由。否则下一个需求会重新问、重新踩。

## Order Matters

```
Step 0   依赖自检 + 宿主能力探测 + 上游契约四锚点（读不到就停）
Phase 1  grilling + domain-modeling → Context Brief（含续接索引、代码库清单、假设登记表、locked 决策索引）
Phase 2  用户确认复杂度 → 检查点／新上下文
   ├─ 不复杂 ─────────────────────────────────┐
   └─ 复杂 → Phase 3  milestone-planning       │
             完整探索与评审（自有 ≤2 轮，超限交用户裁决）
             ↓ DAG 锁定＋环境文档 → 检查点／新上下文 │
Phase 4  writing-plans（一次一个里程碑）←───────┘
         子代理写计划；计划头四段含 Execution Contract，每 Task 内联义务短句
         主代理处理问题与执行选择，判计划可持有性

         subagent-driven-development 或 executing-plans
         → 执行会话写 close-out → finishing-a-development-branch
         ↓ 检查点／新上下文；有下一里程碑才回 Phase 4
```
